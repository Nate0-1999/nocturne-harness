# M3S2 standard-core rescout checklist — EXECUTED 2026-08-18

Derived at claim time from PLAN M3S2, the M2X owner-day checklist's
agent-checkable standard core, and SPEC B.6 rules 1, 8, 9, and 10. Every
owner-facing activation receives a real-browser screenshot. The rescout ends
at findings: no product fix, fix packet, scorer activation, FORCE action,
owner-memory write, cloud mutation, or authentic owner disposition is allowed.

## Real owner-browser walk

1. Open the ordinary Rack from a disposable home under principal and machine
   identity `m3s2-sop-verification`. Confirm there is no FIXTURE curtain and
   the released Palace reports 0.1.5 / schema 0015 / API contract 0.1.4.
2. Create a project-bound thread and submit an ordinary first chat message.
   Confirm the one human gate appears before model output, then keep the gate
   unchanged and receive a real OpenRouter answer with the active model shown.
   This keep is verification-class evidence, never owner training signal.
3. Submit a Unicode-bearing `/remember` fact that is true only of this
   disposable verification run. Confirm a successful save, generated
   keywords, and the new memory visible in the ordinary Memory surface.
4. Submit a second ordinary turn that asks for the saved fact. Confirm there
   is no second modal gate, autonomous re-scoring runs, and the real answer is
   visibly shaped by the saved memory.
5. Open Memory Graph in CURRENT scope. Confirm the saved unit appears after the
   write, selection exposes its text/provenance, and the graph visibly differs
   from its pre-write state.
6. Open Injection Console in CURRENT scope. Confirm the saved unit's scored
   event/contribution state is visible and the active scorer provenance is
   named without invented values.
7. Open Palace Vitals immediately after the real turns. Confirm a live request
   changed spend/receipt state, the displayed lanes remain dollar-honest, and
   no accounting failure blocked chat.
8. Open Context Bars for the same selected thread. Confirm used/capacity are
   the measured request totals, the System/History/Memory/Tools breakdown is
   explicitly estimated, and its categories sum to the displayed used total.
9. Create/select a sibling project and thread. Confirm the project-scoped
   verification memory is absent from its gate, answer, CURRENT Graph, and
   CURRENT Injection Console.
10. Switch back to the original project/thread. Confirm CURRENT Graph,
    Injection, Vitals, and Context follow the shared selection while any
    GLOBAL module remains global.
11. Stop and restart the real daemon against the same disposable home. Confirm
    the durable thread, transcript, actual project binding, memory-backed
    answer, and Graph rehydrate; confirm the journal grew and remains the
    authority. Context observations are daemon-lifetime state and are not
    required to survive this boundary.
12. Use the ordinary theme switcher to select each shipped theme and return to
    NEO-NOIR. Confirm each selection visibly changes the Rack and persists
    across reload. This is mechanical switching only; visual taste is reserved
    for the owner.
13. Wander without a script: move between the chat, Memory, Graph, Injection,
    Vitals, and Context surfaces, operate one reversible module control, and
    record every surprise or friction rather than repairing it.

## Traced proof and hygiene

14. Trace the same browser actions through the disposable journal, Palace
    memory/event/receipt reads, and authenticated health. Preserve only
    sanitized facts: thread/project IDs, memory ID, model/provider, terminal
    state, measured token totals, category sums, and residue status.
15. Tombstone every verification memory by exact ID, confirm it is no longer
    active or injectable, run the bounded credential scan, hash every
    screenshot, and rerun both ordinary product suites.

- Any authentic keep/remove/never disposition, Palace admission, scorer or
  proposal activation, FORCE action, or real-project judgment.
